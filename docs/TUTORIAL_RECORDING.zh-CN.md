# Kaor 完整教程录制流程（中文）

本文是一份可直接照稿录制的桌面端视频教程脚本，覆盖从 GitHub Releases 下载、首次启动、三种识别模式、AI 融合与翻译、人工校对、排版烧录，到日志排障和工作区重置的完整工作流。

教程以 Windows x64 发行包为准。普通观众不需要 Python、Node.js、FFmpeg、CUDA Toolkit、UVR5 或虚拟环境；源码构建不属于本期主流程。界面仅面向桌面端，不安排移动端演示。

> 录制前基准：以当前仓库的 [README](../README.md)、[中文使用手册](USER_GUIDE.zh-CN.md) 和 [故障排查](TROUBLESHOOTING.zh-CN.md) 为功能依据。正式录制前用准备发布的 Release 再走一遍本文检查点，避免界面文字或资产名变化。

## 1. 成片定位

### 1.1 标题建议

主标题：

```text
Kaor 完整教程：从视频 OCR / ASR 提取，到 AI 校正、翻译与字幕烧录
```

封面短标题：

```text
视频自动烤肉机
OCR + ASR + AI 翻译
```

### 1.2 适合人群

录制时明确告诉观众，本软件主要适合：

- 需要翻译动画、访谈、课程、直播回放或其他桌面视频的字幕制作者。
- 只想把画面字幕或语音提取成结构化 CSV，再交给其他工具处理的人。
- 希望视频、音频、OCR、ASR 和烧录都留在本机，只把字幕文本交给 AI 的用户。
- 遇到长驻字幕、渐入字幕、两人同时说话、叠加字幕或不同人物字幕颜色的人。
- 使用 OpenAI 兼容官方接口、中转站、Ollama、LM Studio、llama.cpp 或本地 GGUF 的用户。

不作为主要目标的场景：

- 手机或平板上直接运行完整 AI 工作流。
- 完全无人复核、要求每条字幕百分之百正确的批量生产。
- 只有 AMD 显卡且要求 Windows 下 OCR、UVR5、ASR 全部走 AMD GPU 的工作流。

### 1.3 一句话定位口播

> Kaor 是一个本地优先的视频字幕工作台：字幕模式看画面，音频模式听人声，混合模式把两份证据交给 AI 校正；识别、校对和翻译分开，最后再把译文排版并烧录进视频。

## 2. 录前准备

### 2.1 演示素材

准备一段 60 秒到 3 分钟的可公开演示视频，并确保它同时包含以下测试点：

- 至少三条清晰画面字幕。
- 至少一条持续时间较长的字幕。
- 至少一条渐入或由浅变深的字幕。
- 至少两种字幕颜色。
- 至少一处两人同时说话或第二条字幕后叠上来的片段。
- 一处 OCR 容易错的词，用于演示单帧框选 OCR 和人工修改。
- 清晰人声和少量背景音乐，用于演示 UVR5、静音切分和 ASR。

优先使用自制、获得许可或完全合成的素材。文件名使用无隐私的演示名，例如：

```text
Kaor-Tutorial-Demo.mp4
```

另准备以下内容：

- 一份没有秘密信息的剧情简介、角色资料、术语表和翻译风格。
- 一个专门用于录制的低权限 API Key，或录制完成后剪掉真实 Key 输入画面。
- 一个支持 OpenAI 兼容 `/models` 和 `/chat/completions` 的测试端点。
- 足够的磁盘空间，尤其是 NVIDIA 发行包、ASR 模型、本地 GGUF 和导出视频。

### 2.2 录屏设置

- 推荐画布：`2560 x 1440`，录制 `60 fps`，成片可输出 `1440p` 或缩放到 `1080p`。
- 浏览器缩放保持 `100%`，Windows 显示缩放固定，不在中途改变。
- 打开鼠标高亮；点击关键按钮前停顿约 0.5 秒。
- 录制桌面只保留浏览器、下载目录和发行包目录，不显示私人文件。
- 下载和模型处理阶段可后期倍速，但保留开始、实时进度和成功结果三个镜头。
- 每个耗时操作叠加“实际耗时取决于视频长度、网络和硬件”，不要承诺固定速度。

### 2.3 隐私与密钥遮挡

- 录制前关闭通知、聊天软件和浏览器密码自动填充提示。
- API Key 输入框全程保持密码显示状态；不要点击“显示密钥”。
- 录屏素材、工程文件名、Base URL、自定义 Header 和日志正文中都可能包含隐私，发布前逐帧检查。
- 可以先录制一个假的 `sk-demo-********` 输入镜头，再停录填写真实 Key，恢复录制后只展示“测试连接”结果。
- 即使“导出诊断包”会遮蔽常见 API Key、Bearer Token 和访问令牌，公开视频或分享诊断包前仍要人工检查。

### 镜头 B：版本选择表

在画面中展示以下表格，并逐行口播：

| 发行包 | OCR | UVR / ASR / 说话人 | 本地翻译 | 选择建议 |
| --- | --- | --- | --- | --- |
| CPU | CPU | CPU | llama.cpp CPU | 无独显、虚拟机或兼容性优先 |
| AMD | CPU | CPU | llama.cpp Vulkan 使用 AMD GPU | Windows AMD 显卡用户 |
| NVIDIA | Paddle CUDA 12.6 | PyTorch CUDA 12.6 | llama.cpp CUDA | 驱动兼容的 NVIDIA 显卡 |

关键口播：

> AMD 版当前只有本地翻译可以通过 Vulkan 使用 AMD GPU。Windows 下的 PaddleOCR、UVR5、ASR 和说话人链路仍走 CPU。NVIDIA 版不要求另装 CUDA Toolkit，但需要兼容的显卡驱动。CPU 版最通用，也最慢。

### 镜头 C：下载和校验

CPU/AMD 操作：

1. 下载对应的完整 ZIP 和 `.sha256` 校验文件。
2. 在 PowerShell 中可选执行：

   ```powershell
   Get-FileHash .\Kaor-Windows-x64-CPU.zip -Algorithm SHA256
   ```

3. 把结果与 Release 的校验值比较。
4. 用资源管理器完整解压到普通可写目录，避免直接在压缩包中启动。

NVIDIA 操作：

1. 把 `Kaor-Windows-x64-NVIDIA-Setup.exe`、`Kaor-Windows-x64-NVIDIA.parts.json` 和全部 `.zip.001`、`.zip.002` 等分片下载到同一目录。
2. 不要重命名、漏下或分散存放任何分片。
3. 双击 Setup；它会验证每个分片、重建完整 ZIP、再次校验并解压。
4. Setup 成功后进入生成的程序目录。

录制检查清单：

- [ ] 下载画面包含资产名，但不暴露浏览器账号信息。
- [ ] NVIDIA Setup 显示真实校验过程和成功结果。
- [ ] 明确“发行包无需安装 Python 和 CUDA Toolkit”。
- [ ] 下载或校验耗时部分已倍速，并标注时间压缩。

## 4.5 原字幕 ROI 与译文安全区

### 镜头 A：原字幕区

1. 切换到左侧“框选”。
2. 点击“在画面中重新框选”或画布工具“原字幕框”。
3. 在字幕周围拖出区域。
4. 分别拖动四个顶点和四条边中点，展示 8 点调整。
5. 拖动框体内部，展示整体移动。

口播：

> 四个顶点同时改变横纵边界，四条边中点只移动单边。原字幕区要包含描边、第二行，以及可能晚一点叠上来的第二条字幕，但不要把台标、弹幕和其他文字一起框进来。

### 镜头 B：译文区

1. 点击“调整译文位置”或画布工具“译文框”。
2. 把译文区移动到不会与原字幕重叠的位置。
3. 在两人同时说话的演示帧检查区域高度。

口播：

> 译文安全区是后续 ASS 排版和烧录的位置。它应避开原字幕、人物脸部、界面按钮和关键画面；两条同时说话的字幕还要预留多层高度。

验收清单：

- [ ] 原字幕完整落在黄色区域内。
- [ ] 译文区域没有压住原字幕。
- [ ] 两个区域在横竖比变化后仍位于视频画面内部。
- [ ] 展示了 8 个控制点，而不是只重新画一个矩形。

## 4.6 三种识别模式怎么选

先在右侧“识别来源”展示三个标签，然后给出判断表：

| 模式 | 使用条件 | 输出 | 是否需要 AI |
| --- | --- | --- | --- |
| 字幕 | 画面已有清晰字幕，或视频含可用内嵌字幕流 | `ocr.csv`、当前 `source.csv` | 不需要 |
| 音频 | 无画面字幕、字幕很差，或只想语音转写 | `speech.csv`、当前 `source.csv` | 不需要 |
| 混合 | 重要项目，希望画面文字与人声互相校正 | `ocr.csv`、`speech.csv`，融合后 `source.csv` | 识别不需要；AI 融合需要在线或本地模型 |

口播：

> 字幕提取和翻译是严格分开的。无论选哪个识别模式，都可以先下载 `source.csv`，以后再决定要不要翻译。

## 4.7 字幕模式：高精度 OCR

开始参数演示前先说明：字幕模式会优先读取视频中可用的内嵌字幕流；没有可用字幕流时，才对所选画面 ROI 运行 PaddleOCR。录制素材若同时包含内嵌字幕和烧录字幕，应提前决定本节要展示哪条分支，并在口播中说清楚实际命中的来源。

### 参数镜头

逐项展示并口播：

| 参数 | 录制建议 | 说明 |
| --- | --- | --- |
| 计算设备 | NVIDIA 版选“自动”，CPU/AMD 保持“自动” | 自动会显示真实设备，不按包名虚报 GPU |
| 采样帧率 | 演示保持默认 `4 fps` | 范围 `0.5-12 fps`；更高会增加计算量 |
| 帧批处理 | 保持“自动（按显存）” | 16 GB 档常用 40 帧；OOM 时可手动降低 |
| 高精度共识 | 开启 | 对增强后的同一画面进行多路 OCR 投票，速度较慢 |
| 过滤疑似噪声 | 开启 | 拦截低质量单帧文字、孤立数字和短计数碎片 |

### 运行镜头

1. 点击“开始字幕识别”。
2. 近景展示原字幕区实时出现最新 OCR 文本。
3. 近景展示本地任务卡的“采样 A/B”、设备、批大小、真正 OCR 帧和复用帧。
4. 若视频足够长，展示进度持续变化；后期可倍速。
5. 完成后切到底部 `OCR` 视图，再切回 `最终`。
6. 点击“导出 OCR CSV”和“导出字幕 CSV”。

解释原理的口播：

> 它不是每一帧都无脑 OCR。先在 C++/OpenCV 热路径上判断字幕区域有没有变化，静止字幕复用结果；渐入字幕会等待更清晰的候选帧；长驻字幕会定期复查；最后再按文字、位置和时间合并，减少重复 Cue。识别本体仍是 PP-OCRv6，所以 C++ 优化的是前后处理速度，不是用更低质量模型替换 OCR。

显存说明口播：

> GPU 不一定一直百分之百占用，因为视频解码、变化检测、CPU 预处理、GPU OCR 和写盘是流水线。真正的判断标准是每秒处理速度和任务是否连续推进。若出现 GPU OOM，Kaor 会释放缓存并把失败批次递归二分；也可以手动降低帧批处理。

检查点：

- [ ] `ocr.csv` 至少有一条 Cue。
- [ ] `source.csv` 已同步生成。
- [ ] 长驻字幕没有被拆成大量完全重复的行。
- [ ] 渐入字幕优先保留清晰完整文本。
- [ ] 无意义 `0`、`1` 和短碎片明显减少；仍有误差留到校对章节处理。

## 4.8 音频模式：UVR5、静音切分与 ASR

音频模式有三个独立按钮，也有“一键完成音频三阶段”。先展示独立运行，最后说明一键流程。

### 阶段 1：UVR5 人声分离

| 项目 | 内容 |
| --- | --- |
| 镜头 | 选择“音频”，在“音频三阶段”点击 UVR5 的“运行”。 |
| 口播 | “包内 BS-RoFormer 从 `mix.wav` 分离出 `vocals.wav`。它通过独立的 `KaorAudioWorker.exe` 运行，不调用电脑上其他 UVR5 安装目录。” |
| 操作 | 计算设备保持自动，录下任务进度从模型加载到分离完成。 |
| 检查点 | 任务显示完成；日志没有模型校验或显存错误。 |

### 阶段 2：静音切分全部参数

画面完整展示“三阶段参数”，按下表逐项解释：

| 参数 | 默认值 | 当前范围 | 通俗解释与调参方向 |
| --- | ---: | ---: | --- |
| 静音阈值 | `-34 dB` | `-100..0` | RMS 低于阈值视为静音；越接近 `0` 越容易判为静音，环境噪声大时需谨慎 |
| 最短片段 | `4000 ms` | `100..600000` | 达到这个长度后，才会在合格的中间静音处分段 |
| 最长片段 | `30000 ms` | `1000..600000` | 超过后会在目标附近的低能量点再次切开，控制单片显存和处理时长 |
| 最短静音 | `200 ms` | `10..60000` | 连续静音达到该时长才触发中间切分 |
| 检测步长 | `10 ms` | `1..1000` | RMS 检测和边界搜索粒度；越小越细、计算越多 |
| 保留静音 | `500 ms` | `1..60000` | 切片两端最多保留多少静音，避免切掉词头词尾 |
| ASR 批大小 | `4` | `1..64` | NeMo 每批处理的切片数；显存不足时降低，不改变静音边界 |

参数关系口播：

> 最短片段不能小于最短静音，最短静音不能小于检测步长，保留静音不能小于检测步长，最长片段不能小于最短片段。界面会在失焦时归一化参数；“恢复默认参数”会还原这七项。

录制操作：

1. 先保持默认值点击静音切分的“切分”。
2. 展示读取人声、16 kHz 单声道准备、检测边界和“第 N/总数个切片”。
3. 解释 `speech-16k-mono.wav`、`slices/slice-*.wav` 和 `slices/slices.json` 的用途。
4. 为展示调参，只修改“最短静音”为 `300 ms`，说明这会改变切片，随后恢复默认；不必真的重跑第二遍。

### 阶段 3：语言专用 ASR

1. 在“源语言”选择演示视频的真实语言。
2. 打开“专用 ASR 模型”下拉框，指出“推荐”和“已下载”标记。
3. 若模型缺失，第一次点击任务会自动下载到 `models/asr/`；录下下载开始和完成，过程可倍速。
4. “计算设备”保持自动；NVIDIA 可选 CUDA，CPU/AMD 的音频链使用 CPU。
5. 保持“时间边界精修”和“说话人分离”开启。
6. 点击 ASR 的“打标”，展示切片序号或批次范围持续更新。
7. 完成后切到底部 `ASR` 视图并下载 `speech.csv`。

当前语言列表口播：

> 当前模型目录按语言展示专用模型，覆盖日语、英语、中文、韩语、西班牙语、法语、德语和俄语。不是把所有语言塞进同一个通用模型；未下载模型会在首次任务按需下载。

时间边界精修口播：

> 它先使用 ASR 原生词或段时间戳，再读取 16 kHz 人声的短时能量，在有限窗口内寻找真正的发声开始和结束。相邻非重叠字幕不会被修到互相穿越，本来重叠的说话会保留重叠。

说话人分离口播：

> 如果 ASR 自带说话人标签就优先保留，否则本地 VAD 和声纹嵌入会把发言段聚类，再按时间分配给 Cue。聚类只表示声音相似的一组，不知道角色真名；短句、音乐残留、抢话和相似音色仍需要人工校正。

### 一键三阶段

最后点击“一键完成音频三阶段”但在确认任务启动后取消，说明它会依次复用同一组参数运行 UVR5、切分和 ASR。任务进度大致分布为：

- UVR5：`0%-55%`
- 16 kHz 准备：约 `57%`
- 静音切分：`59%-68%`
- ASR：`68%-100%`

强调 `85%` 通常表示当前处于 ASR 阶段，不代表程序固定卡死；应观察切片计数和日志是否继续更新。

## 4.9 两人同时说话与后叠字幕

用演示素材定位到重叠片段，进行以下讲解：

| 情况 | 正确处理 |
| --- | --- |
| 两人真的同时说不同内容 | 保留两个 Cue，使用同一 `group_id`、不同 `layer`，说话人分别标记 |
| 第一条仍在，第二条稍后叠上来 | 保留两条独立 Cue 和真实各自时间，后出现者使用另一层 |
| 同一句逐字补全或浅色渐入 | 保留最终完整 Cue，删除短暂碎片 |
| OCR 同色但不同人物 | 结合时间、位置、ASR 与人工角色名校正，不只依赖颜色 |

口播：

> `group_id` 表示同一重叠组，`layer` 决定显示层，`track_id` 用于时间跟踪。OCR 颜色和 ASR 声纹都是线索，不是绝对身份。最终应在人工校对中确认。

常见日志口播表：

| 日志或现象 | 解释 | 处理顺序 |
| --- | --- | --- |
| `HTTP 401/403` | Key、权限、余额或请求头问题 | 检查上游控制台、Key 和自定义 Header |
| `HTTP 404` | Base URL、请求路径或模型 ID 错误 | 区分 Base URL 与 `/chat/completions` |
| `HTTP 429` | 额度或速率限制 | 等待、充值或降低并发 |
| `HTTP 524` | 代理已连接，但上游未在约 120 秒完成 | 观察自动拆批；减小请求或换更快模型/端点 |
| `Expecting value: line 1 column 1` | 上游返回空正文、HTML 或非 JSON | 看状态、Content-Type 和响应预览 |
| `missing=['speech.csv']` | ASR 分支没生成文件 | 完成或重跑音频三阶段 |
| GPU 可用但利用率不满 | 解码、CPU 前处理、GPU 推理和写盘交替 | 看吞吐和进度，不只看瞬时利用率 |
| CUDA 不可用 | 包版本、驱动或设备不匹配 | 确认 NVIDIA 包和兼容驱动，不必另装 Toolkit |
| FFmpeg 导出失败 | 片源、音轨编码、路径或包内运行时问题 | 展开完整 stderr，并查维修条目 |

口播：

> 完整错误目录和命令行检查方法都在包内故障排查文档。报错时先复制真实日志，再按匹配条目处理，不要只根据进度百分比猜原因。

## 4.18 任务复用、断点续跑和工作区重置

### 续跑机制

口播并配数据流动画：

> OCR、UVR、切片、ASR、融合和翻译都会记录源文件指纹、参数签名和真实产物。再次提交相同任务时，完整产物直接复用；文件缺失、为零、只有表头或清单不完整时，从第一个不完整阶段继续。OCR、ASR 和 AI 子批还有磁盘 checkpoint。

要点：

- `cache/task-state.json`：任务签名与产物状态。
- `cache/ocr-checkpoint.json`：OCR 最近快照。
- `cache/audio/asr-checkpoint.json`：已完成音频切片。
- `cache/ai/*-checkpoint.json`：AI 已完成 Cue。

### 重置当前工作区

1. 返回“导入”。
2. 确保没有运行中或排队任务。
3. 点击“重置当前工作区”，阅读确认框后确认。
4. 等待重新探测片源并提取新的 `mix.wav`。
5. 展示片源仍在，而字幕表已恢复为空表头。

口播：

> 重置保留原视频、项目设置和清单，但删除 Kaor 生成的缓存、导出、OCR、ASR、译文和旧 `source.csv` 内容，然后重新准备音轨。“删除项目”才会连片源一起删除。重置不是撤销，执行前先导出需要保留的 CSV 和视频。

## 4.19 优点、缺点与选择建议

### 优点

- 本地优先：视频、音频、帧缓存、OCR、UVR5、ASR、校对和烧录留在本机。
- 提取与翻译分离：只提 CSV 时不需要 API Key。
- 三种证据路线：清晰画面用 OCR，无字幕用 ASR，重要项目用混合校正。
- 针对字幕问题做了变化检测、长驻复用、渐入候选、多帧共识、噪声过滤和重叠轨道。
- 音频三阶段可单独重跑，也可一键串联；切分参数完整开放。
- 在线 API、中转站、本地 GGUF 和已有本地服务可以按项目需要选择。
- 人工校对功能完整：三视图、增删改、逐帧、单帧 OCR、人物批量颜色和吸管。
- 任务带真实产物检查和 checkpoint，长任务中断后可以续跑。
- 日志页按错误匹配维修指南，并能导出经过常见凭据遮蔽的诊断包。
- MIT 开源，核心数据使用 CSV，便于审阅和二次处理。

### 缺点和边界

- 高精度 OCR 和混合模式比单一快速 OCR 更慢，NVIDIA 完整包体积也较大。
- 第一次使用某种语言的 ASR、说话人分离或本地翻译时仍需联网下载模型。
- AMD Windows 版的 OCR、UVR5、ASR 和说话人处理当前走 CPU；AMD GPU 只用于 Vulkan 本地翻译。
- 说话人聚类不会知道真实角色名；多人抢话、短句和相似音色仍需人工处理。
- OCR 不能恢复画面中根本看不清或被遮住的文字；渐入、特效字和复杂背景仍可能误识别。
- AI 融合和翻译可能理解错误，低置信度行、专名、数字和重叠对白必须复核。
- 在线 AI 会收到 CSV 和勾选的上下文；中转站的隐私与保留策略由其服务方决定。
- 本地大模型需要额外磁盘、内存或显存，速度和质量取决于所选量化及硬件。
- 硬字幕导出需要重新编码，耗时且可能产生较大文件。
- WebUI 是桌面工作台，不做移动端 AI 使用体验。

### 选择建议口播

> 只追求最快提取，先用字幕模式；没有画面字幕就用音频模式；要做正式翻译成片，优先混合模式，再人工校对。低配置电脑选 CPU 包并缩短素材，AMD 用户接受识别走 CPU，NVIDIA 用户选 CUDA 包。隐私敏感项目使用本地翻译；追求更强语言理解且可接受文本发送时，再使用可信在线接口。
